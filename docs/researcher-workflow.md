# Researcher request workflow

This describes the current development pilot, not the intended finished service. The portal and Convex development deployment are separate from any future production system.

1. **Discover:** A visitor explores the public visualization gallery. Public examples are separate from client requests.
2. **Sign in:** The researcher creates a username/password account or signs in at `/portal`. Account recovery and email verification are not implemented.
3. **Submit:** The researcher submits a title, contact details, visualization type, description and optional HTTPS link to public materials. After submitting, they can upload non-sensitive files on the project page. Confidential materials are not supported. The request starts as `Submitted`.
4. **Review:** The studio administrator signs in to the portal, opens **Studio dashboard**, selects the request and reviews its details. The dashboard has a mailto link; it does not send a message automatically.
5. **Understand the work:** The studio contacts the researcher if needed and begins creating their visualisation. The intended commercial model is subscription-based, but plans, billing, eligibility and subscription management are not implemented yet.
6. **Track:** The administrator selects one of four visible stages: `Received`, `In progress`, `Ready to explore` or `Complete`. These are simple manual progress labels. Changing a stage creates an in-portal unread update for the request owner; no email is sent. Older internal `approved`, `reviewing` and `quoted` values are displayed as `Received` for compatibility and remain unchanged until an administrator chooses a different stage.
7. **Share:** Each portal request has a same-domain project page at `/projects/<request-id>/<title-slug>`. Only the signed-in request owner and studio administrator can fetch its content. The administrator can save one editable entry and attach a scatter plot; both can upload and download project files. A deliverable upload or changed entry creates an unread update. The slug is a readable label and the ID identifies the request; neither is an access credential. Titles appear in URLs, so avoid sensitive titles. Any external preview link must be secured separately at its host. See [Project workspaces](project-workspaces.md) for limitations.
8. **Researcher review:** A signed-in researcher sees the navigation bell and request badge for unread updates, opens their request and can mark the observed update as read. There is no built-in feedback thread, review approval or email notification.
9. **Completion and publication:** The administrator may manually mark a request `Complete`. To publish, the studio prepares a public draft, then the researcher reviews and explicitly approves that version from the private project. The owner can later withdraw it. See [Researcher-approved public pages](publication-workflow.md) for rights, snapshot and production limitations. Delivery remains manual.

The bell counts requests with unread updates among the latest 100 requests returned for an account; it does not count individual update events. Historical updates from before notifications were introduced are not backfilled. The development portal is an unfinished pilot and must not be used for confidential or regulated data until security, storage and operational requirements are met.

The older public `/request` form uses a separate webhook/local-file intake path; those submissions do not appear automatically in the Convex studio dashboard. See [Convex portal setup](convex-portal.md) for access controls, setup and technical limitations.
